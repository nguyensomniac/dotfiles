# UX writing

Write what someone needs to act, understand the current state, and recover.
Before rewriting a string, check whether it needs to exist.

## Read in context

Identify the screen's job, main action, and next step. Inspect surrounding copy,
adjacent states, and code that controls actions and messages. Separate observed
behavior from proposals and assumptions. Reuse existing terminology and wording
when the meaning matches.

## Reduce and write

- Keep, remove, move, or rewrite each string. Remove repeated status,
  confirmations, metadata, and obvious-state eyebrows. Give adjacent headings
  different jobs. Repetition is useful only where it serves another decision.
- Cut explanation and placeholder prose that obscure the action. Move useful
  information to the step where it helps. Preserve necessary instructions,
  feedback, accessibility, and recovery.
- Name what the action actually does. Verify its destination and result;
  flag broken behavior instead of disguising it with copy.
- Prefer a single clear verb for CTAs and action-oriented placeholders when
  context makes it unambiguous. Add words when needed to clarify the target,
  consequence, or expected input. Do not force verbs into input examples or
  replace persistent accessible labels with placeholders.
- Use consistent product terms and plain language appropriate to the audience.
  Do not copy the user's chat voice into the product or expose internal events
  and raw errors.
- When an action fails, is unavailable, or requires another person, explain
  what happened and the next step.

## Deliver

For reviews, use a concise table: location/state, current copy, decision,
replacement or destination, and reason. Include kept copy only when the reason
matters. For one string, give an inline recommendation.

Flag unknown behavior. Ask only when the answer changes the wording or flow.
Implement when edits are requested; a wording question alone needs an answer.
Verify edits in the real affected states, including wrapping, relevant narrow
viewports, and accessible names. Follow existing repository checks and review
requirements. Report changes and verification gaps briefly.
